# Database

Operation Shadow uses PostgreSQL (18.6 locally) through Drizzle ORM and the `pg` driver. The same code and the same
migrations run against local Postgres and Neon; only the connection strings differ.

Everything lives in `packages/db`:

| Path | Contents |
|---|---|
| `src/schema/auth.ts` | Better Auth tables (generated by the Better Auth CLI; regenerate rather than edit) |
| `src/schema/app.ts` | Preferences and audit log |
| `src/schema/generation.ts` | Generated missions, generation jobs, AI usage |
| `src/schema/progress.ts` | Campaigns, mission runs, save slots and revisions |
| `src/repositories/*.ts` | Ownership-scoped query functions |
| `src/client.ts` | `createDbHandle(connectionString, { max })`: a `pg.Pool` (default 10 connections) plus Drizzle |
| `src/readiness.ts` | Readiness check used by `/api/ready` |
| `src/migrate.ts`, `src/migrate-cli.ts` | Migration runner |
| `migrations/` | SQL migrations and Drizzle's journal and snapshots |

JSON columns hold documents whose shapes are defined by Zod schemas in `packages/schemas/src`. The database does not
validate them; the application validates on write and again on read.

## Tables

Conventions:

- Users are identified by `user.id`, a `text` id created by Better Auth. Application tables call it `owner_id`
  (or `user_id`).
- Application tables use `uuid` primary keys generated by Postgres (`gen_random_uuid()` via Drizzle's
  `defaultRandom()`) and `timestamptz` columns. The Better Auth tables use `text` ids and `timestamp` without time
  zone.
- Foreign keys use `ON UPDATE no action`. `ON DELETE` is listed per key.

### Auth tables (`schema/auth.ts`)

Managed by Better Auth through its Drizzle adapter.

**`user`**: one row per player.

| Column | Type | Notes |
|---|---|---|
| `id` | text | Primary key |
| `name` | text | Not null |
| `email` | text | Not null, unique |
| `email_verified` | boolean | Default `false` |
| `image` | text | Nullable |
| `created_at`, `updated_at` | timestamp | Default `now()` |

**`session`**: active sign-in sessions (7-day lifetime).

| Column | Type | Notes |
|---|---|---|
| `id` | text | Primary key |
| `token` | text | Not null, unique |
| `expires_at` | timestamp | Not null |
| `ip_address`, `user_agent` | text | Nullable |
| `user_id` | text | FK → `user.id`, **ON DELETE CASCADE**; index `session_userId_idx` |
| `created_at`, `updated_at` | timestamp | |

**`account`**: sign-in methods linked to a user (Google OAuth, or the dev credential login).

| Column | Type | Notes |
|---|---|---|
| `id` | text | Primary key |
| `account_id`, `provider_id` | text | Not null |
| `user_id` | text | FK → `user.id`, **ON DELETE CASCADE**; index `account_userId_idx` |
| `access_token`, `refresh_token`, `id_token`, `scope` | text | Nullable OAuth tokens |
| `access_token_expires_at`, `refresh_token_expires_at` | timestamp | Nullable |
| `password` | text | Password hash; used only by the dev login |
| `created_at`, `updated_at` | timestamp | |

**`verification`**: short-lived verification values (for example OAuth state).
Columns `id` (PK), `identifier`, `value`, `expires_at`, `created_at`, `updated_at`. Index
`verification_identifier_idx` on `identifier`. No foreign keys.

**`rate_limit`**: Better Auth's request counters. Stored in the database because in-memory limits do not work
across serverless instances. Columns `id` (PK), `key` (unique), `count`, `last_request` (bigint, epoch ms).
No foreign keys.

|---|---|---|

| `schema_version` | integer | Default 1 |
| `settings` | jsonb | Default `{}`. Shape: `preferencesSchema` in `packages/schemas/src/progress.ts` |
| `updated_at` | timestamptz | |

**`audit_events`**: security-relevant events. Never stores secrets.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid | Primary key |
| `user_id` | text | Nullable; FK → `user.id`, **ON DELETE SET NULL** |
| `kind` | text | `AuditKind`: `dev_login`, `sign_in` (every new session, from a Better Auth database hook), `account_deleted`, `save_deleted`, `campaign_deleted`; `sign_out` is reserved and not written yet |
| `metadata` | jsonb | Default `{}` |
| `created_at` | timestamptz | |

| `spec_version` | integer | |
| `generator_version` | text | |
| `seed` | bigint | |
| `title` | text | |
| `spec` | jsonb | `missionSpecSchema` (`packages/schemas/src/mission.ts`); the stored `id` is a placeholder replaced by the key when served |
| `briefing` | jsonb | `generatedBriefingSchema` |
| `level_hash` | text | |
| `report` | jsonb | Validation report from the pipeline |
| `created_at` | timestamptz | |

**`generation_jobs`**: resumable, idempotent generation jobs. A worker claims a job by setting a lease.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid | Primary key |
| `owner_id` | text | FK → `user.id`, **ON DELETE CASCADE** |
| `idempotency_key` | text | From the `Idempotency-Key` header |
| `request` | jsonb | `generationRequestSchema` |
| `seed` | bigint | |
| `stage` | text | Default `queued`; then `drafting`, `validating`, `building`, `ready`, `failed` or `cancelled` |
| `provider` | text | `gemini`, `mock` or `disabled` |
| `lease_until` | timestamptz | Null when no worker holds the job |
| `attempts` | integer | Incremented on every claim; above 3 the job is marked failed |
| `error` | text | Player-safe message only (≤ 200 characters) |
| `mission_id` | uuid | FK → `missions.id`, **ON DELETE SET NULL** |
| `created_at`, `updated_at` | timestamptz | |

Indexes:

- `generation_jobs_owner_key_idx`: **unique** on `(owner_id, idempotency_key)`. This makes job creation idempotent.
- `generation_jobs_owner_created_idx` on `(owner_id, created_at)`: daily quota counts.
- `generation_jobs_active_idx` on `stage`, partial: `WHERE stage NOT IN ('ready', 'failed', 'cancelled')`.

**`ai_usage`**: one row per model call, for quotas and the monthly budget.

| Column | Type | Notes |
|---|---|---|
| `id` | uuid | Primary key |
| `user_id` | text | Nullable; FK → `user.id`, **ON DELETE SET NULL** |
| `job_id` | uuid | Nullable; FK → `generation_jobs.id`, **ON DELETE SET NULL** |
| `purpose` | text | Currently `mission-plan` |
| `provider`, `model`, `status` | text | |
| `input_tokens`, `output_tokens`, `latency_ms` | integer | Default 0 |
| `cost_usd` | double precision | Estimated cost, default 0 |
| `created_at` | timestamptz | |

`(user_id, created_at)`. Because both foreign keys are `SET NULL`, spend rows survive account deletion and still
count toward the monthly budget.

## Migrations

### Files

SQL migrations are generated by drizzle-kit and committed in `packages/db/migrations`. `meta/_journal.json` lists
them in order, and `meta/000N_snapshot.json` holds the schema snapshot after each one.

| File | Adds |
|---|---|
| `0000_initial_schema.sql` | `user`, `session`, `account`, `verification`, `rate_limit`, `audit_events`, `user_preferences`, with their foreign keys and indexes |
| `0001_generated_operations.sql` | `missions`, `generation_jobs`, `ai_usage`, with their foreign keys and indexes (including the unique idempotency index and the partial active-stage index) |
| `0002_campaigns_and_saves.sql` | `campaigns`, `mission_runs`, `save_slots`, `save_revisions`, with their foreign keys and indexes |

### Applying migrations

- `runMigrations(connectionString)` in `src/migrate.ts` opens a single-connection pool and runs Drizzle's
  `migrate()` against the `migrations` folder. Drizzle records applied migrations in
  `drizzle.__drizzle_migrations` and skips them on later runs, so re-running is safe. This entry point is exported
  as `@operation-shadow/db/migrate` and is deliberately not part of the package index, which the web bundle imports.
- `src/migrate-cli.ts` (`pnpm db:migrate`) reads `DATABASE_URL_UNPOOLED`, falling back to `DATABASE_URL`. On Neon the
  unpooled URL is the direct, non-pooler connection. It exits with code 1 if neither is set or a migration fails,
  and never prints the connection string.
- Locally, the Compose `migrate` service runs `pnpm db:migrate` after `db` is healthy, and `make up` runs it before
  `seed` and `app`. Run it by hand with `make migrate`.
- In production, migrations run as a deploy step against the direct URL (implementation plan §11).

### Creating a migration

1. Edit the Drizzle schema in `packages/db/src/schema/*.ts`. For `auth.ts`, regenerate it with the Better Auth CLI
   instead of editing by hand.
2. Generate the SQL:

   ```bash
   docker compose run --rm tools pnpm db:generate
   ```

   This runs `drizzle-kit generate` with `packages/db/drizzle.config.ts` (`strict: true`). It only diffs the schema
   against the last snapshot; it never connects to a database.
3. Review the new `.sql` file, then commit it with the updated `meta/` files.
4. Apply it with `make migrate`. `/api/ready` reports `migrations: pending` until you do.

### Policy

Migrations are forward-only. There are no down migrations; rollback means deploying the previous build, so a new
migration must keep working with the code it replaces (implementation plan §11). Never edit a migration that has
been applied anywhere. The integration test `tests/integration/upgrade.test.ts` checks that a database created by
the first release (0000 only), with data in it, upgrades to the current schema and keeps its data.

## Repositories and ownership

The query functions in `packages/db/src/repositories` are the only way the app reads or writes user data. Every
function that touches a user's rows takes the owner's id as a parameter, and every route handler passes
`session.user.id` from the authenticated session, never an id from the request. Every `WHERE` clause includes the
owner id, so a caller can only see or change its own rows. When a row belongs to someone else, the function returns
`null` or `false`, and the API answers 404.

| File | Functions |
|---|---|
| `preferences.ts` | `getPreferences`, `savePreferences` (upsert on `user_id`) |
| `audit.ts` | `recordAuditEvent` |
| `generation.ts` | `createGenerationJob` (insert, or return the existing job for the same key), `getGenerationJob`, `claimGenerationJob`, `setGenerationJobStage`, `completeGenerationJob`, `failGenerationJob`, `cancelGenerationJob`, `countGenerationJobsSince`, `countActiveGenerationJobs`, `recordAiUsage`, `aiSpendSince`, `getOwnedMission`, `listOwnedMissions` |
| `progress.ts` | `listCampaigns`, `getCampaign`, `createCampaign`, `getOrCreateActiveCampaign`, `updateCampaignProgress`, `setCampaignDifficulty`, `deleteCampaign`, `startMissionRun`, `completeMissionRun`, `listMissionRuns`, `listSaveSlots`, `writeSave`, `readSave`, `deleteSave`, `deleteUserAccount` |

Exceptions, all internal to the generation worker or global by design:

- `setGenerationJobStage`, `completeGenerationJob` and `failGenerationJob` take a job id that the caller has
  already claimed with the owner-scoped `claimGenerationJob`. `completeGenerationJob` uses the claimed job's
  `owner_id` for the new mission.
- `aiSpendSince` sums spend across all users, for the global monthly budget.
- `recordAuditEvent` writes whatever user id it is given (null for account deletion).

Behaviour worth knowing:

- **Job leases.** `claimGenerationJob` is one `UPDATE … RETURNING` that succeeds only for an active job whose
  `lease_until` is null or in the past. It increments `attempts` and sets a new lease. A job claimed more than
  `MAX_JOB_ATTEMPTS` (3) times is marked failed. `setGenerationJobStage` renews the lease and returns `false` if the
  job was cancelled meanwhile.
- **Atomic completion.** `completeGenerationJob` locks the job row (`SELECT … FOR UPDATE`), checks it is still
  active, inserts the mission and marks the job `ready` in one transaction. A cancelled or finished job stores no
  mission.
- **Active-job count.** `countActiveGenerationJobs` counts only active jobs created in the last 10 minutes, so a job
  abandoned long ago does not block new ones.
- **Campaign progress.** `updateCampaignProgress` re-reads the row and updates it only if `version` is unchanged,
  retrying up to 5 times. Two tabs finishing missions at once both count.
- **Mission runs.** `completeMissionRun` updates only a run whose `outcome` is still `running`, so a run finishes
  once.
- **Saves.** `writeSave` upserts the slot, inserts a revision, moves `current_revision_id`, and deletes revisions
  beyond the newest `SAVE_REVISIONS_KEPT` (3), all in one transaction. A failure at any point leaves the previous
  save intact. `readSave` returns the current revision first, then older ones; the web app
  (`apps/web/src/server/saves.ts`) falls back to an older revision when the current one fails its checksum or
  validation.

## Readiness check

`checkReadiness(pool)` in `src/readiness.ts`:

1. Runs `select 1`. On failure: `{ database: 'error', migrations: 'error' }`.
2. Reads `max(created_at)` from `drizzle.__drizzle_migrations` and compares it with `LATEST_MIGRATION_WHEN`, the
   `when` timestamp of the last entry in the `_journal.json` bundled with the build. Equal or later: `ok`;
   earlier: `pending`.
3. If the migrations table does not exist yet: `{ database: 'ok', migrations: 'pending' }`.

`GET /api/ready` returns 200 only when both checks are `ok` (see [api.md](api.md#get-apiready)).

## Account deletion

`deleteUserAccount(db, userId)` deletes the `user` row. Postgres foreign keys do the rest:

| Removed (CASCADE) | Kept, user reference set to NULL |
|---|---|
| `session`, `account` | `audit_events` |
| `user_preferences` | `ai_usage` (spend still counts toward the monthly budget) |
| `missions`, `generation_jobs` | |
| `campaigns`, `mission_runs` | |
| `save_slots`, `save_revisions` | |

`POST /api/v1/account/delete` calls it, then writes an `account_deleted` audit event with no user id and a
truncated SHA-256 hash of the old id, and clears the auth cookies. The integration test
`tests/integration/progress.test.ts` ("account deletion") checks that everything the user owned is removed and
that other users' rows are untouched.

## Local databases

The Compose `db` service creates two databases on first initialisation:

- `operation_shadow`: development data (`DATABASE_URL`, `DATABASE_URL_UNPOOLED`).
- `operation_shadow_test`: disposable database for integration tests (`TEST_DATABASE_URL`), created by
  `infra/docker/postgres/init/01-create-test-database.sql`. See [testing.md](testing.md).
