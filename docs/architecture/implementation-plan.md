### Principles

1. **The engine is the authority.** All gameplay rules live in `packages/engine`: pure TypeScript with no React, three.js or DOM. The browser runs it for play. The server runs the same code to generate and validate levels and to check AI proposals.
2. **Deterministic simulation.** Fixed 20 Hz ticks and a seeded PRNG stored in state. No wall-clock time or `Math.random` inside the simulation. Rendering interpolates between ticks.
3. **AI proposes, rules decide.** Gemini output is untrusted data. It is schema-validated and checked against catalogs, and it can only take effect through engine commands.
4. **One code path for local and production.** Same app, same `pg` driver, same migrations; the two differ only in environment variables.
5. **Gameplay never waits on the network,** except to load a mission or to save.

## 3. Simulation engine (`packages/engine`)

### 3.1 Core

- **State.** World state is plain serializable data: units, guards, world objects, alarm, objectives, director, planning, stats and RNG state.
- **Level data.** Static data (terrain, nav grid, occlusion, light) is generated once and stored. Dynamic changes such as opened doors, cut fences and destroyed walls are derived from object state and re-applied on load.
- **Commands in.** Inputs are `Command`s (move, stance, ability, interact, cancel, queue, signal, director event). Each is validated before being applied at a tick boundary.
- **Events out.** Outputs are domain events (spotted, noise, alarm change, objective update, damage, and so on). The UI, audio, telemetry and debrief statistics consume them.
- **Determinism scope.** The same build in the same JavaScript engine reproduces a run exactly. Saves hold the full state, so loading never depends on floating-point behaviour differing between browsers.
- **Main thread.** The simulation runs on the main thread (target ≤2 ms per tick). Heavy jobs such as level decoding or bulk path queries can move to a Web Worker if profiling shows the need.

### 3.2 Navigation

**Grid model:**
- A layered 0.5 m grid: one ground layer plus platform patches (towers, walls, piers, ship decks).
- Patches are joined by links: ladders, stairs, climb points and boat embark points.
- **Per-cell data:** walkable flag, surface type, cover height and movement cost. Surfaces are grass, gravel, mud, sand, snow, wood, metal, concrete, shallow water and deep water.

**Pathfinding:**
- **Capability-aware A*:** each specialist has a nav profile. For example, only the Marine enters deep water and only the Infiltrator climbs walls and poles. Paths are smoothed so units can move at any angle, not just along grid lines.
- **Dynamic obstacles:** doors, gates, cut fences and destroyed obstacles update the grid as they change.
- **Unreachable destinations** produce explicit feedback plus the nearest reachable alternative. Path previews come from the same pathfinder.

**Why custom TypeScript rather than Recast or navcat:** it is deterministic, runs identically in the browser and on the server, is easy to test, and is fast enough at this scale (maps of about 200 m × 200 m, roughly 160k cells per layer).

### 3.3 Line of sight, light and concealment

- **Occlusion (2.5D).** A terrain heightfield plus up to two vertical blocking spans per cell. Walls, windows, crates, sandbags and roofs block; a window, for example, is a wall with a gap at eye height. Vegetation adds concealment instead of blocking.
- **Sight test.** A 3D grid-traversal (DDA) ray runs from the guard's eye to a point on the target whose height depends on stance: standing 1.7 m, crouched 1.0 m, prone 0.3 m.
- **Light grid.** Ambient light from time of day and weather; static lamps, baked with occlusion; dynamic searchlights, flares, fires and guard lanterns.
- **Visuals follow gameplay.** Graphics settings never change what a guard can see.

### 3.4 Perception and suspicion

**Two-zone vision cone** (preserved from the reference, T1):

| Zone | Standing or running | Crouched | Prone |
|---|---|---|---|
| Near | seen | seen | seen |
| Far | seen | detected slowly | invisible |

**Suspicion:**
- A continuous value per guard–target pair.
- Rate = base × zone × stance × light × motion × concealment × weather × guard alertness × difficulty. It decays while the target is unseen.
- Thresholds on this value drive the guard state machine (§3.6).

**Disguise:**
- Rank-and-file guards ignore a disguised Deception Specialist unless they see suspicious actions: carrying a body, running near guards, entering restricted areas, attacking or lockpicking.
- Officers see through the disguise at close range over time.
- Being seen changing clothes breaks the disguise.

**What the player sees:**
- Shaped icons above guards (an eye that fills, then "?", then "!") and off-screen direction markers.
- Cone colours that also carry patterns.
- No raw numbers.

### 3.5 Sound propagation

- **Noise events** carry a level in dB at 1 m, a type and a source.
- **Received level** = source level − distance loss − attenuation from walls, doors and terrain crossed (grid ray) − building envelope.
- **Hearing:** a guard hears a sound if the received level exceeds the local noise floor plus a threshold. Rain, surf, machinery and sirens raise the floor.
- **Footsteps** depend on surface and gait: running on metal is far louder than crawling on grass.
- **Other noises:** gunshots, explosions, shouts, thrown lures, noise devices and alarms.
- **Consistency with the UI:** the noise area shown for a unit or action is computed by the same function (T4).
- **Uncertainty:** hearing produces a stimulus with position uncertainty that grows with distance, which leads to an investigation.

### 3.6 Guard behaviour (deterministic state machine)

**States:**
- *Calm:* Idle, Patrol, Observe.
- *Escalating:* Suspicious, Investigate, Search, Challenge, Alerted, Combat.
- *Recovering:* ReturnToPost.
- *Disabled:* knocked out, restrained or dead.
- *Situational:* Escort (marching a captured operative to the holding area), Revive (helping a knocked-out colleague), RaiseAlarm.

**Rules:**
- An explicit transition table with conditions, timers and recovery rules.
- Bounded memory: at most 6 stimuli, which decay over time.
- Temperament (passive, standard, strict, aggressive) and rank come from guard archetypes.

**Communication:**
- Shouts are noise events, so walls and distance matter.
- Radios spread information within a sector.
- Patrols notice a missing post guard.
- Searches visit generated search points (cover, doorways, bushes) in a deterministic order.

**Capture and challenge (T9).** A guard may order an operative in the near zone to halt. If the operative complies, they are escorted to a holding area where the squad can rescue them. Fleeing or attacking escalates to combat and raises the alarm.

**Adaptive update frequency.** A guard's perception runs every tick within 40 m of any operative, every 2nd tick at 40–80 m, and every 4th tick beyond that. The schedule depends only on simulation state, so it stays deterministic.

### 3.7 Alarm ladder

Five levels:

| Level | Name |
|---|---|
| 0 | Routine |
| 1 | Local suspicion |
| 2 | Active investigation |
| 3 | Sector alert |
| 4 | Full alert |

**Effects** are defined per level and include:
- patrols converging on the area;
- guards pairing up;
- gates closing;
- searchlights switching on;
- reinforcements leaving the barracks;
- sirens that raise the noise floor;
- detection multipliers.

**Decay:** levels fall back over time, but never below a post-incident floor.

**Map features:** alarm bells, radio rooms and barracks can all be interacted with, so sabotaging them limits escalation. Any mission that fails at a given alarm level says so in its briefing.

### 3.8 Combat, damage and casualties

**Hit model.** Hits are resolved with the seeded RNG from range, stance, cover, accuracy and difficulty. Operatives are fragile.

**Downed operatives (Standard preset):**
- At 0 HP an operative is downed and a bleed-out timer starts.
- The Field Medic can revive them; anyone carrying a field dressing can stabilize them.
- Death fails the mission.

**Veteran preset:** harsher in every respect.

**Enemy casualties:**
- A knocked-out guard wakes after a timer unless restrained.
- A knocked-out guard who is found gets revived and starts a search.
- A dead body that is found escalates the alarm more sharply.

### 3.9 Specialists and abilities

**Ability interface.** Every ability implements one shared interface. Before use it validates:
- role;
- range and line of sight;
- inventory and charges;
- cooldown;
- stance and carry state;
- mission state and target type.

When an ability is refused, the interface returns a reason code that the UI shows (for example "No line of sight" or "Needs wire cutters"). AI-generated content cannot bypass this check.

| Specialist | Signature kit (◦ = nonlethal) |
|---|---|
| Infiltrator | silent takedown (◦ knockout or lethal), ◦ restrain/gag, climb walls and poles, fast body carry, ◦ remote noise lure |
| Recon/Marksman | binoculars (tag enemies, reveal routes and cones at range), suppressed rifle (few rounds), ◦ tranquilizer darts |
| Combat Engineer | wire cutters, lockpicking, timed and remote charges, sabotage (alarms, radios, searchlights, generators → blackouts), ◦ noise traps |
| Deception Specialist | disguise (uniform from a knocked-out officer or a locker), ◦ hold a guard in conversation (fixes his gaze), ◦ sedative syringe, forged papers for checkpoints |
| Field Medic | revive and treat, ◦ chloroform takedown, smoke canisters (block sight), fast carry of wounded |
| Marine Operator | swim and dive (hidden underwater outside the near zone), inflatable boat (carries 3), silent harpoon, climb from water onto piers and hulls |
| Everyone | pistol (loud), one field dressing, ◦ thrown-stone lure, slow body drag, ladders, doors |

Campaign equipment adds choices: before each mission, the loadout screen hands out extra items from a limited campaign stockpile.

### 3.10 Objectives, extraction and failure

**Objective types:** reach a location, acquire intel, disable a facility, rescue, sabotage, recover an item, evacuate, secure a zone, and optional tasks.

**Each objective is data:**
- prerequisites;
- completion and failure conditions, written in a small typed condition language (data, not code);
- alternative paths;
- reveal rules;
- presentation.

**Extraction** requires every required objective to be complete, with all living operatives and any rescued VIPs inside the extraction zone.

**Unwinnable states** (T20). A monitor watches the objective graph. If the mission becomes impossible, for example because a key item was destroyed or the only route was lost permanently, the mission ends explicitly and the reason is shown.

### 3.11 World director (Option B)

**Event catalog:** every event type has typed parameters. Examples:
- shift changes, convoys and trains;
- weather shifts, dusk turning to night;
- officer inspections, reinforcement patrols;
- opportunities (an unattended truck, an open gate);
- intel reveals and new optional objectives.

**Sources:**
1. the mission's pre-validated timeline;
2. a deterministic fallback deck for each template;
3. runtime AI proposals (§8.4).

**Precondition checks** run on every event before it is applied. Examples:
- spawns happen out of the operatives' sight;
- no new mandatory objective may make the mission unwinnable;
- each difficulty preset has a budget for complications.

**Campaign links:** results set campaign flags that later missions read. For example, destroying the radar removes air patrols from mission 4.

### 3.12 Planning mode (Option C, optional)

- **Tactical pause:** Space pauses the game. You queue orders per operative and see ghost paths with engine-estimated durations.
- **Synchronized actions:** mark actions "wait for signal", then fire them all at once with Enter.
- **Conditional cancellation:** "abort if spotted" and "abort on alarm".
- **Timeline panel:** one row per operative.
- **Execution speed:** 0.5×, 1× or 2×. The same control works as fast-forward while waiting for patrols, which addresses a criticism of the original.
- **Par time is measured in simulation time,** so pausing to plan is never penalized.

### 3.13 Scoring

**Inputs:**
- time against par;
- detections and peak alarm level;
- injuries and downs;
- optional objectives;
- equipment used.

**Output:** a rank from S to D, plus medals such as Ghost (never detected), Restraint (zero kills) and Untouchable (no injuries).

Kills never add points (T12).

## 4. Level generation and validation

**Templates.** Each template is a deterministic layout grammar:

| Template | Contents |
|---|---|
| Coastal | harbour village, piers, gun battery, cliffs, beach |
| Alpine | snow outpost, radar station, pine forest; footprints matter here |
| Rail depot | rail yard, warehouses, fuel depot, scheduled trains |

Each template defines:
- terrain profile and zones;
- structure slots and road generator;
- patrol and post slots;
- objective slots;
- insertion and extraction zones;
- lighting presets;
- its event deck.

**Pipeline.** The generator takes a mission spec and seed and produces, in order:
1. terrain and surfaces;
2. roads;
3. structures;
4. cover and props;
5. vegetation;
6. patrols and posts;
7. objectives;
8. spawns and extraction;
9. nav, occlusion and light grids;
10. validation;
11. a generation report (seed, versions, counts, timings and check results) and a level hash.

**Validation checks:**
- schema validity and catalog references;
- the objective dependency graph is acyclic;
- with the selected squad's movement capabilities, every required objective and the extraction are reachable;
- required items are reachable;
- stealth feasibility: every required objective has an approach that avoids permanently watched near zones, or offers distraction or cover;
- resource limits on entities, triangles and guards.

**Where levels are generated:**
- **Generated missions:** levels are generated on the server (Node) once and stored as a compressed blob that the client downloads. Terrain is therefore identical in every browser, whatever floating-point differences exist between JavaScript engines.
- **Authored missions:** generated at build time by the content build, which fails the build if any authored mission doesn't validate.

## 5. Rendering, art direction and assets

### Look

A stylized-realistic "miniature diorama":
- PBR materials, with one curated palette per theme;
- a strong sun with cascaded shadows, plus fog;
- AgX tone mapping and colour grading for each time of day;
- readable silhouettes;
- optional tilt-shift.

### Scene

- **Terrain:** chunked heightfield with a splat shader blending CC0 material sets (grass, dirt, gravel, rock, snow, sand).
- **Water:** shader with shoreline foam.
- **Buildings:** procedural and modular, merged per material. Roofs are separate meshes for cutaways, and walls dither out when they block the camera's view of the squad.
- **Props and vegetation:** instanced.
- **Characters:** skinned meshes with animation.

### Tactical overlay

- **What it shows:** cones (near and far), noise areas, path previews, planned routes and footprints.
- **How:** everything is drawn into one top-down render target, which terrain and floors sample. Overlays follow the terrain at a fixed cost.
- **Same source as the AI:** cones come from the engine's own visibility fans, so what is drawn always matches what guards see (T2, T3).

### Characters

- **Models:** CC0 rigged humanoids with a shared CC0 animation library. Quaternius packs are the candidates, with the licence verified for every file.
- **Silhouettes:** models are re-tinted and given procedural gear so each role is distinct.
- **Fallback:** procedural mannequins.

### Asset pipeline

1. `tools/assets` downloads pinned CC0 sources: Poly Haven, ambientCG, Quaternius and Kenney.
2. It processes them with glTF-Transform: prune, dedup, meshopt, resize, and KTX2 texture compression where the encoder is available (WebP otherwise).
3. It writes the results to `public/assets`.

**Manifest:** each asset records id, type, source URL, licence, resolution, material config, LODs, memory budget, required/optional status and fallback.

**Robustness:** processed outputs are committed, so builds never depend on third-party sites. A missing optional asset degrades gracefully, and every critical asset has a fallback.

### Graphics settings

- **Presets,** plus individual controls for resolution scale, anti-aliasing, shadows, effects (AO, bloom, DOF), texture quality, draw distance and vegetation density.
- **Tools:** a built-in performance HUD and a fixed benchmark run.

### Performance budgets

These are targets to be confirmed by profiling, not assumed.

| Budget | High (60 FPS) | Low (30 FPS) |
|---|---|---|
| Draw calls | ≤ 600 | ≤ 300 |
| Visible triangles | ≤ 2.0 M | ≤ 0.6 M |
| GPU texture memory | ≤ 768 MB | ≤ 256 MB |
| Shadow-casting lights | sun (3 cascades) + ≤ 2 spotlights | sun (1 cascade) |
| Characters animated at full rate | ≤ 24 (the rest at half rate; off-screen frozen) | ≤ 12 |
| Active sound voices | ≤ 32 | ≤ 24 |
| Simulation | 20 Hz fixed with staggered perception; ≤ 2 ms per tick with 60 guards on the M5 Pro | same rules |
| JS heap | ≤ 400 MB | ≤ 300 MB |
| Mission download | ≤ 60 MB | ≤ 35 MB |

## 6. Camera, input and HUD

### Camera

- Isometric default (about 50° pitch); free or 45°-snap rotation; zoom.
- Pan with WASD, the arrow keys, or optional edge scrolling.
- Focus on and track the selected unit; reset.
- Keeps clearance above terrain and stays inside the map bounds.
- Roof and wall cutaways; a reduced-shake option.

### Selection

- Click a unit, use the portrait bar or number keys, Shift for multi-select, or drag a box.
- Group commands.
- Distinct markers for selected, active, injured, hidden, downed and captured operatives.

### Orders

- **Basics:** right-click for the context action; double-click to run; stance keys; Shift to queue; cancel.
- **Feedback:** a path preview, and explicit "can't reach" or "can't do" messages.

### HUD

Anchored to the screen edges, with no permanent labels on the battlefield (T31):
1. portraits with health and status;
2. context action panel;
3. ability and equipment bar;
4. tactical minimap;
5. objectives;
6. enemy info with a cone/line-of-sight toggle (Shift-click one enemy; hold Alt for all);
7. suspicion and alarm indicator;
8. event log;
9. pause and planning controls, with the timeline;
10. settings.

### Accessibility

- Full key remapping with conflict detection; mouse sensitivity; edge-scroll settings.
- UI scale from 75% to 150%; subtitle size and background.
- Colourblind palettes, with cones also coded by pattern; warnings that always use an icon plus text, never colour alone.
- Keyboard-navigable menus.

**Out of scope, and documented as such:** mobile/touch and gamepad.

## 7. Audio and dialogue

### Mixing and spatial audio

- **Buses:** ambient, music, operative voices, enemy voices, tactical effects, UI and briefing. Each has its own volume control, plus a master.
- **Spatial audio:** the Web Audio `PannerNode` handles distance attenuation and direction.
- **Occlusion:** sounds are muffled (low-pass filtered) based on the engine's count of walls crossed.
- **Environment:** indoor and outdoor ambience; surface-specific footsteps; distinct alert stingers.

### Adaptive music

The score moves through states (stealth → tension → alert → combat → resolution) by crossfading stems.

### Dialogue manager

- **Each line carries:** speaker, context, trigger, priority, cooldown, subtitle, optional voice asset, playback state and interruption rules.
- **Variety:** recent-history tracking prevents repetition, and a verbosity setting controls how chatty the squad is (T22).
- **Priority:** urgent tactical callouts pre-empt chatter.
- **Subtitles:** every line has one.

### Original content plan (no licensed game audio; amended per §15)

- **Sound effects:** synthesized (DSP), plus CC0 audio packs (Kenney) where synthesis falls short.
- **Music:** pre-generated with Lyria 3.5 / Lyria 3 Clip from prompts that share key and tempo per family, so stealth, tension, alert and resolution tracks can crossfade. Shipped as compressed audio.
- **Voices:** a voice bank pre-rendered with Gemini TTS, using the approved casting (one prebuilt voice per character). Every line is stored with its subtitle, speaker, context and cooldown metadata.
- **Fallback:** subtitles plus radio-click cues whenever a voice file is missing. AI-written lines in generated missions are shown as subtitles.

## 8. AI generation (`packages/ai`)

### 8.1 Providers

| Provider | Behaviour |
|---|---|
| `gemini` | Uses the `@google/genai` SDK with structured output via `responseJsonSchema`. Model ids are pinned through environment variables. |
| `mock` | Returns fixtures, including malformed outputs, for tests. |
| `disabled` | Always uses the deterministic fallback, clearly labelled "Offline generator". This is the default until a key exists. |

`GOOGLE_API_KEY` is server-only. It never reaches the client, logs or API responses.

### 8.2 Mission package (versioned schema)

**Contents:**
- title and premise;
- template id, plus environment (time of day, weather);
- objectives by type and slot, optional objectives and extraction;
- squad size, required capabilities and recommendations;
- enemy composition by zone and archetype, and patrol archetypes;
- opportunities, interactables and complications, all chosen from catalogs;
- dialogue lines (speaker ids and contexts);
- briefing and debrief templates;
- difficulty and variation parameters.

**What the model may choose:** only ids, slots, counts and enum values. The deterministic generator turns those choices into coordinates. Free-form geometry, code, URLs and HTML are never accepted.

### 8.3 Generation jobs

Jobs are stored in the database, resumable and idempotent.

**Pipeline:**
1. `POST /api/v1/generation-jobs` with an `Idempotency-Key` creates the job.
2. The server requests a mission package from the model.
3. It validates the package. If validation fails, it makes one repair attempt.
4. It generates the level.
5. It validates reachability and winnability.
6. It persists the mission. If generation failed, it falls back to a deterministic package built from the same template and seed.

**How a job advances:**
- Each stage is claimed atomically with a lease.
- `after()` starts the job immediately.
- The loading screen's progress polling (`/advance`) keeps driving it.

**Limits:**
- No database transaction stays open during a model call.
- Each call has a 45 s timeout.
- Retryable errors (429, 5xx) get at most 2 retries with backoff.
- Jobs can be cancelled, and stale jobs expire.

**Loading screen:** it shows the real stage and always offers a fallback, so a player can never be stuck on it indefinitely.

### 8.4 Runtime events

1. The client sends `POST /api/v1/missions/:id/events/propose` with a compact context built only from enumerated values.
2. The server checks ownership, rate limits and budget.
3. Gemini picks an event from the mission's allowed catalog.
4. The server checks the schema and every catalog and entity reference, stores the event and returns it.
5. The client engine re-checks preconditions against the live state, then applies or rejects the event; either way it is logged.

Gameplay never waits for this exchange. Without AI, the director's fallback deck keeps the world moving.

### 8.5 Safety, budgets and debrief

- **Validation:** Zod schemas with size limits on every string and array. Unknown types are rejected, and coordinates are never accepted from the model.
- **Content safety:** Gemini safety settings, plus a server blocklist covering slurs, real extremist names and symbols, URLs and markup. All generated text is rendered as plain text only.
- **Usage accounting:** a usage table records tokens, estimated cost, latency and status for every call.
- **Spending limits:** per-user daily quotas, a per-campaign budget, and a global monthly cap (`AI_MONTHLY_BUDGET_USD`). Generated missions are cached and reused.
- **Debrief narrative:** the model receives only verified statistics, and its output is checked so that every number matches them. If the check fails, a templated debrief is used. The model never invents accomplishments.
- **Media (images, text-to-speech):** behind feature flags, cached by content hash, and never blocking gameplay.

| Table | Purpose |

- **Connections:** at runtime the app uses the pooled URL, with `attachDatabasePool` on Vercel. Migrations use the direct URL.

### 9.3 Saves

**Contents:** a complete, versioned snapshot of the simulation state (including mission id, seed, positions, guard states, objectives, inventory, timers, director/AI events and RNG state), plus camera position and selection.

**Saving:**
1. The browser gzip-compresses the snapshot.
2. The server checks size limits, decompresses it and validates it with Zod.
3. It cross-checks the mission, campaign and owner.
4. It commits the new revision and moves the slot pointer in a single transaction, so a save is never half-written.
5. It keeps the last 3 revisions for recovery.

**Loading:**
1. The checksum is verified; a corrupt revision falls back to the previous one.
2. Older save versions pass through a chain of migrations.
3. The engine checks invariants before play resumes.

**Save types:**
- manual saves;
- quicksave (F5) and quickload (F9);
- autosaves at checkpoints: when an objective completes, when a mission phase changes, and every 5 minutes while no guard is alerted.

If the network fails, a pending copy is kept locally in IndexedDB until it can be uploaded.

### 9.4 API

**Conventions:** versioned `/api/v1/*` route handlers with Zod request and response contracts, and an error envelope that never leaks internals.

**Endpoint groups:**
- preferences and campaigns;
- mission runs (start and complete);
- missions (spec and level);
- generation jobs and runtime events;
- saves and usage;
- client-error telemetry.

**Health checks:**
- `/api/health`: liveness.
- `/api/ready`: database reachable and migrations applied.

## 10. Security

### Threat model

| Threat | Description |
|---|---|
| Insecure direct object reference (IDOR) | changing an id to read another user's data |
| Budget abuse | burning the AI budget through generation endpoints |
| Prompt injection | crafted input steering the model |
| Unsafe AI text | harmful or broken generated content |
| XSS | script injected through rendered text |
| CSRF | forged state-changing requests |
| Secret leakage | keys exposed in bundles, logs or responses |
| Dependency vulnerabilities | known flaws in third-party packages |
| Oversized payloads | requests large enough to exhaust resources |

### Controls

- **Input:** Zod validation everywhere, plus body-size limits.
- **Access:** ownership scoping, rate limits, and Origin checks on state-changing requests.
- **Browser hardening:** CSP and security headers; no `dangerouslySetInnerHTML`.
- **Prompts and AI output:** only enumerated player choices reach prompts, plus an optional sanitized codename of at most 40 characters. All AI output is treated as untrusted.
- **Logging:** logs are redacted (pino) so passwords, tokens and keys never appear.
- **Dependencies and secrets:** `pnpm audit`, plus a test that scans the client bundle for secrets.

A threat-model document and a security checklist are deliverables.

## 14. Risks, dependencies and compromises

### Risks

| Risk | Mitigation |
|---|---|
| Scope: six specialists, a five-mission campaign and the full platform add up to a very large build | Strict milestone gates; systems before content; missions share templates and the generator; lower polish per mission (accepted in your scope answer) |
| Visual quality of procedural and CC0 art, especially characters and animation | One art direction, palette and shader treatment; procedural gear for distinct silhouettes; mannequin fallback |

| No voice actors | Gemini TTS voice bank pre-rendered at build time (approved samples); subtitles plus radio cues as the fallback |

| Gemini models change or prices rise | Model ids set through env vars; budgets assume the 2027 prices; caps enforced |
